Overview

The Turing Service runs entirely on a single Google Compute Engine VM, orchestrated with docker-compose.prod.yml. This guide covers production-grade deployment to GCP.

Architecture

  • Compute Engine VM: Single e2-medium instance running all services
  • Services:
    • FastAPI backend (port 8005) — voice call orchestration, client management, call analysis
    • Next.js frontend (port 3001) — multi-tenant admin console with real-time dashboards
    • PostgreSQL 17 (port 5432) — pgvector enabled for semantic search in call analysis
    • Redis 7 (port 6379) — session auth, rate limiting, task queues

Cost Breakdown

  • Self-managed on single VM: ~$35/month (e2-medium + storage)
  • Managed services (Cloud SQL + Memorystore): ~$66/month (higher reliability, auto-backups)

Capacity

This configuration comfortably handles:

  • 20+ concurrent client tenants
  • 20,000+ outbound calls per day
  • Sub-50ms API response times under normal load

Prerequisites

Before starting deployment, ensure you have:

  • GCP Project with billing enabled (create at console.cloud.google.com)
  • Domain name (e.g., turing.docstribe.com) with DNS control
  • Git access to https://github.com/nishant-sagar172/turing_service
  • gcloud CLI installed locally and authenticated
  • Bolna voice engine API key (from Bolna dashboard)
  • LLM API key (OpenAI or Anthropic, for call analysis)
Tip: Run gcloud auth login and gcloud config set project YOUR_PROJECT_ID before proceeding.

GCP Infrastructure Setup

3.1 Create Compute Engine VM

Launch a Compute Engine instance in a region near your users. We use asia-south1-a for India.

gcloud compute instances create turing-prod \
  --zone=asia-south1-a \
  --machine-type=e2-medium \
  --image-family=ubuntu-2204-lts \
  --image-project=ubuntu-os-cloud \
  --boot-disk-size=30GB \
  --boot-disk-type=pd-ssd \
  --tags=turing-server

3.2 Reserve Static IP

Allocate a static external IP for your domain DNS A record:

gcloud compute addresses create turing-ip --region=asia-south1
gcloud compute addresses describe turing-ip --region=asia-south1 --format='get(address)'
# Attach to VM
gcloud compute instances delete-access-config turing-prod --zone=asia-south1-a --access-config-name="External NAT"
gcloud compute instances add-access-config turing-prod --zone=asia-south1-a --address=STATIC_IP

3.3 Firewall Rules

Open ports for HTTPS traffic and Bolna webhooks:

# HTTPS (frontend + API)
gcloud compute firewall-rules create turing-allow-https \
  --allow=tcp:443,tcp:80 \
  --target-tags=turing-server \
  --source-ranges=0.0.0.0/0

# Webhook from Bolna (optional: if accepting direct webhooks)
gcloud compute firewall-rules create turing-allow-bolna \
  --allow=tcp:8005 \
  --target-tags=turing-server \
  --source-ranges=13.203.39.153/32

3.4 DNS Configuration

Point your domain's A record to the static IP:

A record: turing.docstribe.com  →  STATIC_IP

Wait 5-10 minutes for DNS propagation before proceeding to Caddy setup.

VM Setup

4.1 Install Docker

SSH into your instance and install Docker:

gcloud compute ssh turing-prod --zone=asia-south1-a

# On the VM:
sudo apt update && sudo apt upgrade -y
sudo apt install -y ca-certificates curl gnupg
sudo install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/ubuntu/gpg | sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] https://download.docker.com/linux/ubuntu $(lsb_release -cs) stable" | sudo tee /etc/apt/sources.list.d/docker.list
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-compose-plugin
sudo usermod -aG docker $USER
# Log out and back in for group change

4.2 Clone Repository

git clone https://github.com/nishant-sagar172/turing_service.git
cd turing_service

Deploy

6.1 Start Infrastructure

Start PostgreSQL and Redis first (they take a few seconds to initialize):

cd ~/turing_service
docker compose -f docker-compose.prod.yml --env-file .env.prod up -d postgres redis

Verify both containers are healthy:

docker ps  # should show (healthy) within 30s

6.2 Run Database Migrations

Create all tables and indexes:

docker compose -f docker-compose.prod.yml --env-file .env.prod run --rm migrate

This creates 13 tables including: clients, calls, batches, agent_catalog, and more.

6.3 Start Backend + Frontend

docker compose -f docker-compose.prod.yml --env-file .env.prod up -d

6.4 Verify Deployment

Check all containers are healthy:

docker ps  # All 4 containers should show (healthy)

Test backend liveness:

curl http://localhost:8005/health

Test backend readiness (DB connected):

curl http://localhost:8005/health/ready

Test frontend (should return 200):

curl -s -o /dev/null -w "%{http_code}" http://localhost:3001/login
Note: Frontend may take 1-2 minutes to build on first run. Check logs with docker logs -f turing-prod-frontend.

SSL/TLS with Caddy

Caddy automatically provisions Let's Encrypt certificates and handles HTTPS termination, proxying to the backend on localhost:8005 and frontend on localhost:3001.

7.1 Install Caddy

sudo apt install -y debian-keyring debian-archive-keyring apt-transport-https
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/gpg.key' | sudo gpg --dearmor -o /usr/share/keyrings/caddy-stable-archive-keyring.gpg
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/debian.deb.txt' | sudo tee /etc/apt/sources.list.d/caddy-stable.list
sudo apt update
sudo apt install caddy

7.2 Configure Caddyfile

sudo tee /etc/caddy/Caddyfile << 'EOF'
turing.docstribe.com {
    # Frontend (console UI)
    reverse_proxy localhost:3001

    # Backend API + webhooks (direct access)
    handle /v1/* {
        reverse_proxy localhost:8005
    }
    handle /health* {
        reverse_proxy localhost:8005
    }
    handle /webhooks/* {
        reverse_proxy localhost:8005
    }
    handle /docs {
        reverse_proxy localhost:8005
    }
    handle /openapi.json {
        reverse_proxy localhost:8005
    }
}
EOF
sudo systemctl restart caddy

Caddy will automatically request and install a Let's Encrypt certificate for your domain.

Verify SSL: Visit https://turing.docstribe.com/health in your browser. You should see a JSON response with no SSL warnings.

Webhook Integration

8.1 How It Works

  • When placing calls/batches, the backend sends TURING_PUBLIC_URL to Bolna as the callback URL
  • Bolna sends status updates (answered, completed, failed, etc.) to {TURING_PUBLIC_URL}/webhooks/voice
  • The webhook handler validates the source IP against VOICE_WEBHOOK_ALLOWED_IPS
  • On validation, the webhook updates the call status in the DB and triggers outcome notifications
  • Terminal states (completed, failed, no_answer) trigger optional LLM-based call analysis

8.2 Verify Webhook Endpoint

Test that your webhook endpoint is publicly accessible (from your local machine):

curl -X POST https://turing.docstribe.com/webhooks/voice \
  -H "Content-Type: application/json" \
  -d '{"id": "test-123", "status": "completed"}'
# Should return 422 (validation failed) or 200 (success)

A 422 response means the endpoint is reachable but the payload is unrecognized (expected for test data).

8.3 Bolna Dashboard Configuration

No manual webhook URL configuration needed. The backend automatically sends TURING_PUBLIC_URL as the callback URL when creating calls via the Bolna API. Verify in Bolna dashboard that the webhook is being triggered for your calls.

Client Onboarding

After deployment, register and enable your first client.

9.1 Register First Client

curl -X POST https://turing.docstribe.com/v1/register \
  -H "Content-Type: application/json" \
  -d '{"name": "kalaam-continental", "contact_email": "ops@continental.hospital"}'

9.2 Approve Client

curl -X POST https://turing.docstribe.com/v1/admin/clients/{client_id}/approve \
  -H "X-Admin-Key: YOUR_ADMIN_KEY"

9.3 Enable Agents

Sync agents from Bolna and enable them for the client:

# Sync agents from Bolna
curl -X POST https://turing.docstribe.com/v1/admin/agents/sync \
  -H "X-Admin-Key: YOUR_ADMIN_KEY"

# Enable specific agents for the client
curl -X PUT https://turing.docstribe.com/v1/admin/clients/{client_id}/agents \
  -H "X-Admin-Key: YOUR_ADMIN_KEY" \
  -H "Content-Type: application/json" \
  -d '{"agent_ids": ["agent-uuid-1", "agent-uuid-2"]}'

9.4 Client Gets API Key

Clients can claim their API key via the console, or you can generate one:

curl -X POST https://turing.docstribe.com/v1/admin/clients/{client_id}/keys \
  -H "X-Admin-Key: YOUR_ADMIN_KEY"

9.5 Update Kalaam Backend Configuration

Set this in Kalaam's .env:

TURING_BASE_URL=https://turing.docstribe.com

Maintenance

10.1 Daily PostgreSQL Backups

Set up a cron job to back up the database daily:

mkdir -p ~/backups

# Add to crontab (crontab -e):
0 3 * * * docker exec turing-prod-postgres pg_dump -U turing turing_db | gzip > /home/$USER/backups/turing_$(date +\%Y\%m\%d).sql.gz

10.2 Updating Code

Deploy new versions with zero downtime:

cd ~/turing_service
git pull origin main
docker compose -f docker-compose.prod.yml --env-file .env.prod build
docker compose -f docker-compose.prod.yml --env-file .env.prod run --rm migrate
docker compose -f docker-compose.prod.yml --env-file .env.prod up -d

10.3 Viewing Logs

Monitor services in real-time:

# All services
docker compose -f docker-compose.prod.yml logs -f

# Backend only
docker logs -f turing-prod-backend

# Last 100 lines with timestamps
docker logs --tail 100 -t turing-prod-backend

10.4 Restart Services

docker compose -f docker-compose.prod.yml --env-file .env.prod restart backend frontend

Troubleshooting

Common issues and their fixes:

Symptom Cause Fix
Backend won't start Missing or invalid env vars Check docker logs turing-prod-backend — Pydantic will show which field is missing or invalid
"Operator login not configured" OPERATOR_SESSION_SECRET not set Set OPERATOR_SESSION_SECRET in .env.prod, then restart frontend
Webhook returns 403 Source IP not in allowlist Add Bolna's egress IP to VOICE_WEBHOOK_ALLOWED_IPS in .env.prod
Webhook returns 422 "cannot be attributed" Call not in database or unknown execution ID Verify the call was placed through Turing (check DB directly: SELECT * FROM calls WHERE id='...';)
Frontend returns 500 "backend not reachable" TURING_API_URL wrong at build time Rebuild frontend with correct TURING_API_URL=http://backend:8005
DB connection refused PostgreSQL not healthy or not started Run docker ps, check postgres logs with docker logs turing-prod-postgres
"email-validator not installed" Old Docker image without dependency Rebuild backend: docker compose -f docker-compose.prod.yml build backend
SSL cert not provisioning DNS not pointed or port 80/443 blocked Verify DNS A record points to static IP. Check firewall allows :80 and :443. Run sudo systemctl status caddy to see errors.
